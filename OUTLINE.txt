# Project: Multimodal Cross-Platform OS Controller

Build a local-first multimodal operating-system control framework that allows users to control their computer through multiple input modalities:

1. Voice commands
2. Hand gestures
3. Keyboard/mouse events
4. Eventually head movement, gaze, custom sensors, and other modalities

The application must support **Linux and macOS as first-class platforms**.

Initial Linux target:

* Arch Linux
* Hyprland
* PipeWire

Initial macOS target:

* macOS
* Native macOS Accessibility APIs
* AppleScript / Shortcuts where appropriate
* Native application and window-management interfaces where available

The system should convert every input modality into a common structured intent and then safely execute that intent through a platform-specific OS adapter.

---

# Core Architecture

The fundamental architecture is:

```text
                 ┌─────────────────────┐
                 │    Voice Input      │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │ Speech Recognition  │
                 └──────────┬──────────┘
                            │
                            │
┌──────────────┐      ┌─────▼─────┐      ┌───────────────┐
│ Hand Camera  │ ───► │ Normalize │ ◄─── │ Keyboard/Mouse │
└──────────────┘      └─────┬─────┘      └───────────────┘
                            │
                            ▼
                  ┌──────────────────┐
                  │ Laya Decision    │
                  │ Model            │
                  └────────┬─────────┘
                           │
                           ▼
                  Structured Intent
                           │
                           ▼
                  ┌──────────────────┐
                  │ Policy / Safety  │
                  │ Layer            │
                  └────────┬─────────┘
                           │
                    ┌──────▼──────┐
                    │ OS Adapter  │
                    └──────┬──────┘
                           │
                 ┌─────────┴─────────┐
                 ▼                   ▼
             Linux                macOS
                 │                   │
             Hyprland           Accessibility
             PipeWire           AppleScript
             D-Bus              Shortcuts
             playerctl           Native APIs
```

The **input, decision, intent, policy, logging, and action-definition layers must remain platform-independent**.

Only the final execution layer should contain OS-specific implementation.

# Core Design Principle

Laya is the **decision layer**, not the OS execution layer.

Never allow Laya or another model to generate arbitrary shell commands and execute them.

Instead, Laya chooses from a predefined action vocabulary and produces strongly validated structured intents.

Example:

```json
{
  "action": "switch_workspace",
  "parameters": {
    "workspace": 3
  },
  "confidence": 0.98
}
```

The OS adapter determines how that intent is executed.

Linux might use Hyprland IPC.

macOS might use the appropriate macOS workspace/window-management mechanism.

Laya should not know or care which operating system is executing the intent.

# Platform Architecture

Use an abstraction similar to:

```python
class OSController:
    def execute(self, intent):
        raise NotImplementedError
```

Then implement:

```text
os/
├── base.py
│
├── linux/
│   ├── controller.py
│   ├── hyprland.py
│   ├── audio.py
│   ├── media.py
│   ├── applications.py
│   └── windows.py
│
└── macos/
    ├── controller.py
    ├── accessibility.py
    ├── audio.py
    ├── media.py
    ├── applications.py
    └── windows.py
```

The application should select the correct implementation at runtime.

For example:

```python
controller = get_os_controller()
controller.execute(intent)
```

Do not scatter OS checks throughout the application.

Avoid architecture such as:

```python
if linux:
    ...
elif macos:
    ...
```

throughout unrelated modules.

# Input Normalization

Every input source must produce a normalized event.

Voice:

```json
{
  "type": "voice",
  "text": "switch to workspace three"
}
```

Gesture:

```json
{
  "type": "gesture",
  "name": "swipe_right",
  "confidence": 0.95
}
```

Keyboard:

```json
{
  "type": "keyboard",
  "key": "MEDIA_PLAY_PAUSE"
}
```

The rest of the system should not need to know where the event originated.

# Laya Decision Layer

Create a model abstraction:

```python
class DecisionEngine:
    def decide(self, event):
        ...
```

Implement:

```python
class LayaDecisionEngine(DecisionEngine):
    ...
```

Laya should map normalized inputs into strongly typed intents.

Example:

```json
{
  "action": "open_app",
  "parameters": {
    "application": "firefox"
  },
  "confidence": 0.97
}
```

Another:

```json
{
  "action": "volume_up",
  "parameters": {
    "amount": 10
  },
  "confidence": 0.93
}
```

The rest of the application should depend on `DecisionEngine`, not directly on Laya.

This allows future replacement with another model.

# Policy / Safety Layer

Never execute model output directly.

Every intent must pass through:

```text
Laya
 ↓
Intent validation
 ↓
Policy
 ↓
OS Controller
```

The policy layer must:

1. Verify the action exists.
2. Validate parameters.
3. Check confidence.
4. Reject malformed intents.
5. Reject unsupported actions.
6. Prevent arbitrary command execution.
7. Log the decision.
8. Require confirmation for potentially destructive actions.

Never support model-generated:

```text
run_shell_command
execute_command
sudo
delete_file
format_disk
```

as unrestricted actions.

If shell commands are required internally, they must be hard-coded by the platform adapter rather than generated by the model.

# Linux Adapter

Support:

* Arch Linux
* Hyprland
* PipeWire

Use appropriate Linux interfaces:

* Hyprland IPC / `hyprctl`
* PipeWire / `wpctl`
* `playerctl`
* D-Bus
* application launchers
* native Linux APIs where appropriate

Examples:

```text
switch_workspace
→ Hyprland

volume_up
→ PipeWire / wpctl

next_track
→ playerctl

open_app
→ desktop/application launcher
```

Do not make the core architecture dependent on Hyprland.

Hyprland should be an implementation of the Linux window-manager adapter.

Eventually allow:

```text
Linux
├── Hyprland
├── GNOME
└── KDE
```

without changing the decision system.

---

# macOS Adapter

Support macOS as a first-class platform.

Use appropriate macOS-native mechanisms such as:

* Accessibility APIs
* AppleScript
* Shortcuts
* application launching
* native window-management mechanisms
* media-control APIs where available
* macOS audio controls

Examples:

```text
open_app
→ macOS application launching

focus_window
→ Accessibility APIs

window movement
→ Accessibility APIs / supported window-management mechanism

media control
→ appropriate macOS media interface

volume
→ native macOS audio-control mechanism

lock_screen
→ appropriate macOS system interface
```

The macOS implementation should not simply execute Linux commands through compatibility layers.

Use native macOS mechanisms where practical.

If macOS requires user-granted Accessibility permissions, detect the missing permission and provide a clear error explaining what permission is required.

Never attempt to bypass macOS security controls.

# Engineering Requirements

1. Cross-platform core.
2. Linux and macOS are first-class platforms.
3. Arch Linux + Hyprland is the first Linux target.
4. macOS is the first Apple target.
5. Keep OS-specific code isolated.
6. Use native APIs where possible.
7. Local-first architecture.
8. Strongly typed intent schemas.
9. Never execute arbitrary model-generated shell commands.
10. Validate every model decision.
11. Handle low-confidence predictions gracefully.
12. Log decisions and execution results.
13. Make Laya replaceable.
14. Make speech recognition replaceable.
15. Make gesture recognition replaceable.
16. Make OS backends replaceable.
17. Write tests before expanding functionality.
18. Do not bypass OS security or permission mechanisms.
19. Do not require internet connectivity for basic OS control.
20. Do not overwrite existing user projects without inspecting them first.

# AI Coding Agent Instructions

Act as a senior cross-platform systems engineer.

Before writing substantial code:

1. Inspect the repository.
2. Detect the current OS.
3. Detect desktop/window manager where applicable.
4. Inspect existing code that may be reusable.
5. Check installed Python/tooling versions.
6. Check available OS utilities/APIs.
7. Determine which dependencies are already installed.
8. Do not overwrite existing files blindly.
9. Implement one stage at a time.
10. Run tests after each meaningful change.
11. Keep platform-independent code separate from platform-specific code.
12. Document architectural decisions briefly.
13. Avoid unnecessary dependencies.
14. Prefer native OS interfaces over brittle automation.
15. If an API is uncertain, inspect its current documentation rather than guessing.

The final application should be a real runnable cross-platform tool, not a conceptual prototype.

Start by inspecting the repository and environment, then implement **Stage 1: the platform-independent event → intent → policy → OS-controller architecture**.

Do not implement later stages until the Stage 1 architecture is working and tested.
